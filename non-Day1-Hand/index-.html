1 Section 1

Shared Workspace Structure

Agree on the minimum before opening any tool. Six fields. Clear meaning. Consistent rules.

Core idea: Structure before tools. If the team hasn't agreed on what to track and what each field means, every tool they build into will drift.

The 6 minimum fields — click each to see what it means

Reference ID Unique identity
A stable unique code for each task. Used to match a task across tools, files, and conversations. Example: LC-001 for Launch Campaign task 1.
Task Name Free text
What the work is — specific enough for anyone on the team to understand. Not "email thing." Try: "Write Instagram caption — product launch".
Owner Controlled
One person accountable for moving the task forward. Must come from the agreed list — not a team, not "TBD." Mona / Tareq / Danielle / Lina.
Status Controlled
Where the work stands — agreed values only. To Do / In Progress / In Review / Done. No "almost done," no "nearly there."
Due Date Real date
A real calendar date — not "ASAP" or "next week." A date that can be filtered, sorted, and matched to a calendar. Example: April 15.
Priority Controlled
An agreed urgency level — Low / Medium / High / Critical. Not "urgent!!!" — that is not a filterable value.

Field · Value · Rule — three different things

Field
Status
The column label — what category of information it is
→
Value
In Review
The specific entry that goes inside the field
→
Rule
"Only move to In Review once the brief is complete"
The agreed behaviour for how the value is used
⚠ Without structure
  • "almost done" / "in progress" / "doing" — all the same stage
  • Mona / Mona H. / Mona Hamza — all the same person
  • "next week" / "ASAP" / "April" — all the same kind of deadline
✓ With structure
  • Status: In Progress — one agreed value, filterable
  • Owner: Mona — one agreed name, consistent everywhere
  • Due Date: 15 April — one real date, sortable
Key takeaway: The 6 fields are the minimum. Team + Role are not part of this minimum — they come later as optional support columns.

3 Section 3

Lookup Logic and Connected Data

Stable support data — like Team and Role — should be entered once and pulled automatically. Not retyped into every row.

Without vs with a reference table

Without lookup
With lookup
  • Tareq — Design — Designer (row 3)
  • Tareq — Publishing — Publishing Coord. (row 4, after move)
  • Danielle — "design review" (row 5 — wrong team name typed)
  • Result: Tareq appears as two people. Filters break. Reports are wrong.
  • Tareq → lists lookup → Team: Design, Role: Designer (always accurate)
  • When Tareq moves to Publishing: update one row in Lists tab → all rows update
  • Result: one source of truth. Zero manual retyping. No drift.

VLOOKUP — click each part to understand it

IFERROR( VLOOKUP(C2, Lists!$E$2:$G$5, 2, FALSE), "Not found" )
Search key
C2
The Owner cell in this row — the value to look for in the reference table
Range
Lists!$E$2:$G$5
The Owner/Team/Role table in the Lists tab — locked with $ so it doesn't shift when copied
Index
2
Return column 2 of the range — Team. Use 3 for Role.
Exact match
FALSE
Only return a result if the owner name matches exactly — no guessing
Owner is the lookup key because it is controlled. A controlled key = reliable lookup. A free-typed key = broken lookup.
4 Section 4

Automation with Google Apps Script

Automation comes after the data is structured, controlled, and connected. Never before.

The rule: Automate repeated actions. Do not automate human judgment.
✓ Automate now
  • Last Updated At — timestamp on every edit
  • Review Started At — when Status → In Review
  • Completed At — when Status → Done
  • Deadline reminder emails
→ Maybe later
  • Reminder emails (need reliable owner email data)
  • Status summaries to Slack/email
✕ Never automate
  • Deciding priority level
  • Assigning task ownership
  • Deciding if work is ready for approval
  • Anything that needs business judgment

7 Section 7

Process Rules and Handoff Logic

Tools don't stay aligned by themselves. A short operating note keeps the three-tool workflow consistent and owned.

Without operating rules: Status changes in one tool but not others. Task names drift. Due dates disagree. Nobody knows who owns the next step.

Who updates what — and when

When Sheets Notion Board
New task created Add row — all 6 fields Add brief if needed Add card — same name as Sheets
Status changes Update Status ← task record (update Sheets first) Only if brief outcome changes Move card to match Sheets status
Due date changes Update Due Date ← agreed record Update if brief references it Update card date to match Sheets

Handoff logic — stage by stage

Content → Design
Copy approved internally · Brief includes audience, message, format · Designer assigned and notified · Sheets → In Review
Design → Approval
Final asset linked in brief · Handoff note added: what was delivered, what to review, any risk · Reviewer named and notified · Sheets → In Review
Approval → Publishing
Approval outcome recorded in brief · Any changes completed · Sheets → Done · Publishing team receives asset + brief link + publication date
Publishing → Complete
Published link added to brief · Sheets confirmed Done · Board card moved to Done and closed
Naming rule: Same task name in Sheets, Notion, and the board — no variations. Same status values exactly. Same owner names. If names drift, the system stops matching itself.

8 Section 8

Using AI to Support the Workflow

AI comes last — on purpose. It is most useful when the workflow already exists. AI drafts, summarizes, transforms, and suggests. It does not own, approve, or decide.

✓ AI should help with
  • Rewriting vague task titles into clear cards
  • Drafting first-pass handoff notes
  • Summarizing a long brief into bullet points
  • Suggesting pre-publishing checklists
  • First drafts of process notes / SOP sections
  • Formula help or script drafting in Sheets
✕ AI should not own
  • Deciding if work is ready for approval
  • Assigning final task ownership
  • Changing status to Done without human confirmation
  • Setting final priority without business context
  • Replacing the handoff note requirement

Weak vs strong AI request

⚠ Weak request
"Write a task."
No context. No format. No constraints. AI will guess — and guess wrong.
✓ Stronger request
"Rewrite 'Email thing for launch' into a clear board card title under 10 words. Add a one-sentence scope note. Owner: Mona. Tool: Trello."
Context + task + format + constraints + input. Output is useful with light editing.

AI flow: draft → human review → final output

Rough input to AI
"launch email - mona is doing copy, goes out april 15, cta is sign up page, danielle approves, maybe legal too"
AI first draft
Objective: Send launch email on April 15 to drive sign-ups.
Owner: Mona. Approver: Danielle. CTA: Sign-up page.
Legal review: [TBC]
Human checks before using
Confirm sign-up page URL · Confirm legal requirement · Verify April 15 matches Sheets · Add exact CTA wording once copy approved

📋 Cheat Sheet

Quick reference — the key rules

The 6 minimum fields
  • Reference ID — unique task identity
  • Task Name — what the work is
  • Owner — one person accountable
  • Status — agreed stage: To Do / In Progress / In Review / Done
  • Due Date — a real calendar date
  • Priority — agreed level: Low / Medium / High / Critical
Tool roles
  • Sheets — task records, status, dates, owner data
  • Notion — briefs, context, process notes (source for workspace knowledge)
  • Board — execution visibility, movement, ownership
  • Lists tab — source of controlled values and reference data
  • When tools disagree on task data → update Sheets first
Lookup rule
  • Owner is the lookup key because it is controlled
  • Team + Role are pulled via VLOOKUP from Lists tab
  • Team + Role are NOT part of the minimum 6
  • Change Team/Role in Lists tab → all rows update
Automation rule
  • Automate: timestamps, status-based markers
  • Never automate: priority, ownership, approval
  • Last Updated At → onEdit trigger
  • Review Started At / Completed At → status trigger
Handoff rule
  • Handoff = status change + note + next owner assigned
  • Note must include: what delivered, what to review, any risk
  • Next owner must be named and notified — not assumed
  • Completion confirmed by receiver, not self-reported
AI rule
  • AI: draft, summarize, transform, suggest
  • AI never: approve, assign, decide readiness
  • Good request = context + task + format + constraints
  • Always human-review before using AI output
⚠ Common Mistakes

What goes wrong — and how to fix it

🔴
Confusing field with value
"Status" is the field. "In Progress" is the value. Agreeing on field names is not enough — agree on the values too. Fix: define both before building.
🔴
Free-typing where control is needed
Status, Owner, and Priority typed freely = filters break, lookups fail, reports lie. Fix: data validation dropdowns from the Lists tab.
🔴
Retyping stable support data
Team and Role typed manually in every row = drift when someone changes teams. Fix: reference table + VLOOKUP. Enter once, reuse everywhere.
🔴
Automating judgment calls
Automating priority or approval readiness = the system overrides human decisions it can't make. Fix: only automate timestamps and trigger-based markers.
🔴
Building Notion as a second tracker
Different status values, different owner names in Notion = two systems the team must maintain. Fix: Notion is context. Sheets is the record. Same names everywhere.
🔴
No operating rules
Tools without rules drift within days — status in one place, different status elsewhere. Fix: write the operating note. Make update rules and handoff logic explicit.
