Session Overview

What Day 4 is really about.

Day 4 is not a Git command lesson. It teaches the collaboration layer that makes engineering work visible, reviewable, safe to merge, and traceable after the work leaves one engineer’s machine.

Core idea: A change is not ready because code exists. It becomes ready when it is isolated, explained, reviewed, approved, merged, and released with enough evidence that the team can trust it.

Before Day 4

The work is defined

Requirements, Jira structure, AI-assisted implementation thinking, and evidence have already shaped the work.

During Day 4

The change becomes collaborative

The feature enters repository workflow: branch, commit history, pull request, review, merge, and release awareness.

After Day 4

The team can judge movement

Learners can explain how a code change moves safely through team engineering systems without becoming hidden or chaotic.

Day Journey

The collaboration path.

Use this journey as your map while reviewing the workshop. Each step answers a different collaboration question.

S1
Repo-ready change
Can the work item be stated as one bounded, testable change that someone else can understand?
S2
Branch isolation
Can the change live in a branch that protects the main line and clearly connects to the tracked work?
S3
Commit history
Can the history explain the change step by step instead of forcing the reviewer to reconstruct it?
S4
Review-ready PR
Does the PR title, summary, evidence, tests, and risk note help the reviewer before opening the diff?
S5
Code review
Can reviewer and author reduce ambiguity through clear comments, responses, and decision-making?
S6
Merge + release
Does the team understand that approval, merge, deployment, and production impact are related but not identical?
Core Rules

The rules to remember.

These are the mental shortcuts learners should carry into assignments, interviews, onboarding, and real team work.

Repo

Define before branching

If the change cannot be stated in one sentence, the branch will inherit the ambiguity.

Branch

One branch, one story

A branch should isolate one bounded change, not become a container for unrelated discoveries.

Commit

History is communication

A commit is a readable checkpoint, not just a save point. The message should reveal the step.

Review

PRs are handoffs

A PR should frame the change for the reviewer before the reviewer reads the full diff.

Weak collaboration trail
Branch name hides the purpose.
Commit messages say “fix,” “changes,” or “final.”
PR description repeats the title and provides no evidence.
Review comments are vague or personal.
Merge is treated as the same thing as production release.
Stronger collaboration trail
Branch name connects to the exact behavior or ticket.
Commits show the feature progression step by step.
PR explains purpose, tests, risk, and reviewer focus.
Review comments reduce ambiguity and name the required action.
Merge, deploy, and release are understood as different moments.
Detailed Notes

Section-by-section handout.

Click each section to review the key idea, what to remember, and what to avoid.

1
From ready work item to repo-ready change
+

A repository does not need a vague idea. It needs a bounded change that can be explained, isolated, reviewed, and tested.

  • The carried-forward feature is the auto-escalation trigger on SLA breach.
  • A stronger change sentence names the condition, action, and observable outcome.
  • Repo readiness means the change is narrow enough to hand to someone else.
  • Do not use the branch to discover the requirement for the first time.
Memory line: “A change becomes collaborative when someone else can understand what it is supposed to do before reading every line of code.”
2
Isolating the change with a branch
+

A branch protects the shared main line while the change is still being built and reviewed.

  • Main is a shared line. Unreviewed work should not live there directly.
  • A good branch name makes purpose visible before the diff opens.
  • The same workflow logic appears in different vocabulary across GitHub, GitLab, and Bitbucket.
  • A branch is a decision, not a reflex.
Branch-start check
Scope
One bounded change, not multiple tickets compressed into one branch.
Trace
The branch connects back to a work item, story, or ticket.
Name
The branch name shows what behavior is being added, fixed, or changed.
3
Recording usable commit history
+

A well-isolated branch can still be hard to review if the history inside it is unreadable.

  • A commit is a readable checkpoint in the change.
  • Commit messages should say what changed and why that step matters.
  • Weak messages push reconstruction work onto the reviewer.
  • Strong history makes PR writing and review easier.
Weak messages
updates
fix
final changes
Stronger messages
add SLA breach detection logic
record escalation event on threshold breach
add tests for SLA auto-escalation trigger
4
Turning the change into a review-ready PR
+

A pull request is a reviewer handoff surface, not a code dump.

  • The title should name the behavior, not just say “update.”
  • The summary should explain what changed and why.
  • The PR should tell the reviewer where to focus.
  • Tests, screenshots, logs, risks, or known limits should be visible when relevant.
Useful PR description structure
Purpose
What problem or ticket does this change address?
Change
What behavior, files, or modules changed?
Evidence
What tests, checks, logs, or manual validations support it?
Risk
What should the reviewer watch carefully?
5
Code review as shared engineering judgment
+

Code review is not a personal audit. It is shared quality control around one specific change.

  • The reviewer checks behavior, risk, readability, maintainability, and tests.
  • A review comment should reduce ambiguity, not add to it.
  • Comments can be questions, suggestions, or required changes.
  • Author responses should explain what changed and why, not only say “done.”
Question

Used when the reviewer needs clarification.

Suggestion

Used when the reviewer proposes an improvement but may not block merge.

Request

Used when the reviewer identifies a blocking issue.

6
Merge, release, and environment awareness
+

Approval removes one barrier. It does not automatically mean the code is in production.

  • A PR can be approved but still blocked by checks, conflicts, or pipeline failures.
  • Merge means the code joins the shared repository line.
  • Deployment moves code to an environment.
  • Release means users or teams are actually affected by the change.
  • Some decisions deserve a short ADR or release note so future readers understand why the change exists.
Memory line: “Merged code is shared. Production code is live. Those are not the same thing.”
Quick Reference

Day 4 cheat sheet.

Use this as the fast review before an assignment, PR review, or technical interview.

Repo-ready: one bounded behavior, known scope, visible test expectation, traceable to a work item.
Branch: isolates the change and makes the purpose visible before the diff opens.
Commit: records a meaningful step, not just a save point.
PR: frames purpose, change, evidence, risk, and reviewer focus.
Review: checks the change with shared judgment and precise feedback.
Merge/release: separates approval, repository merge, deployment, and production impact.

The complete Day 4 move.

Take one real change from the earlier days and make it safe for a team to collaborate around it. The goal is not to memorize tool buttons. The goal is to preserve the story, evidence, and responsibility of the change as it moves through the engineering system.
