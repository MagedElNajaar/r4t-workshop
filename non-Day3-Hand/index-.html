How this session is structured

The session follows a deliberate progression: it begins with thinking and judgment (what is worth automating and why), moves through structured planning (mapping the workflow before opening any tool), enters tool-based building in two environments, and closes with reliability, complexity, testing, and AI-assisted refinement. Each stage depends on what came before it.

1
Identifying repeated workflows and automation opportunities
25 min · Light concepts
▾
  • The session begins with repeated workplace tasks that move across tools — form submissions, tracker updates, notifications, approvals, and follow-up actions. Learners look at where manual effort accumulates across a connected workflow.
  • The content clarifies which kinds of repeated work are suitable for automation and which parts still require human review. The distinction between automatable and human-required steps is the foundational judgment this stage develops.
  • This section ends with a set of realistic automation candidates that are suitable for workflow building — specific, grounded, and ready to carry into the next stage.
Key mindset shift

The session challenges the common impulse to automate everything. Good automation thinking is specific: which exact steps are repeated, rule-based, and add no value when performed by a human? That is a much smaller set than everything a team finds inconvenient.

Try it yourself
Think about the last time you waited for someone to review something, had to send a follow-up reminder, or manually copied data from one tool into another. Which of those steps was truly judgment-free?
This reflection is the starting point for identifying your own automation candidates.

Why map before building

Automation does not fix an unclear workflow — it runs the confusion faster, at scale, without anyone noticing until something breaks. Mapping forces every assumption to be stated explicitly before a tool is opened.

Explaining APIs and connected-tool logic in a practical way
25 min · Light concepts
▾
  • The session focuses on how tools exchange information inside an automation workflow, without turning the topic into a theory-heavy block. The goal is practical understanding, not technical depth.
  • The content covers API concepts at a working level: how one tool sends data, how another receives it, and how connected actions are triggered across a multi-tool workflow. The emphasis is on what this means in practice during a build — not on the underlying engineering.
  • This section ends with a usable understanding of how cross-tool automation works, sufficient for learners to follow and build the Zapier and n8n workflows in the next stages.
Practical framing

An API

Application Programming Interface — a set of rules that allows one tool to send information to another. In automation, APIs are how Zapier and n8n talk to Google Sheets, Slack, and other apps.
is the messenger between tools. When a status field changes in your tracker, the API tells the automation platform — which then triggers the next step. Understanding this flow is enough to build and troubleshoot reliably.

Building the first workflow in Zapier
40 min · Tool-heavy
▾
  • The session moves into the first live automation build inside Zapier, using the workflow map produced in Stage 2 as the build specification.
  • The content covers trigger setup, field mapping, transformation steps, action configuration, and basic workflow testing — all within a real automation sequence connected to the team's existing tools. Zapier
  • This section ends with a working Zapier automation that completes a realistic cross-tool task — specifically the status-change notification workflow mapped in the previous stage.
Before moving to the next step, always ask
If this trigger fired for the wrong row — what would the team notice first? The wrong person notified, the wrong task name, or the workflow running at the wrong time?
This check reveals whether the trigger is precise enough to be trusted in a real workflow.
Testing the output — not just the run

A green success message inside Zapier is not sufficient. The real test is whether the notification that arrives gives the recipient everything they need to act — without asking a follow-up question. Task name, owner, due date, and brief link should all be present and correct.

Adding safe design and workflow control

  • The content covers input validation, retries, logging, basic rate-limit awareness

What happens
The trigger fires correctly. The action runs. But the recipient field resolves to nothing — the tool either sends to no one, throws a silent error, or logs a false success. The approver has no idea the task is waiting.
Scenario B
Someone typed "in review" instead of "In Review" — capitalisation off.
Click to see what happens →
What happens
The trigger checks for an exact string match. The row is never detected. The workflow never starts. No error is logged — because nothing triggered at all. The task silently misses the handoff.
Scenario C
The status field was saved twice in quick succession.
Click to see what happens →
What happens
Both saves trigger the automation. The approver receives two identical notifications within seconds — and assumes two separate tasks were submitted. Duplicate triggers erode trust in the system faster than almost any other failure type.
Scenario D
The brief link exists but points to an old version of the file.
Click to see what happens →
What happens
The validation check passes — the field is not empty. The notification sends. The approver opens the link and finds the wrong version. Automation can verify that data exists; it cannot verify that data is correct.
The larger point about failure

A workflow that runs without errors is not the same as a workflow that works. Every failure scenario above produced a completed run with no alert — but the wrong output reached the wrong person, or no one at all. Safe design means the workflow knows when it should stop, not just when to proceed.

Extending the workflow with branching, approvals, and failure paths
30 min · Medium
▾
  • The session moves into more advanced workflow control, where not every case follows the same linear path. A single trigger can lead to multiple different outcomes depending on the data and conditions it encounters.
  • The content covers conditional routing, approval steps, alternate paths, failure paths, and return-to-owner logic — as well as the audit-trail thinking that helps teams understand what the workflow did and why it did it.
  • This section ends with a more complete automation structure that can handle three distinct workflow outcomes: continue automatically, wait for approval, or return to the owner with the reason why.
The three-path branching model

Continue automatically — All required fields are present. No flags triggered. The task passes validation and moves forward to the approver without any human intervention required. Speed is the priority on this path.

Escalation path — A task has been at the approval gate beyond the defined time window, or is flagged as urgent. The workflow notifies the team lead rather than the original approver, including wait time and risk level. The workflow does not proceed until a human responds.

Testing the workflow and estimating business impact
20 min · Light
▾
  • The session closes the build phase by validating the automation against the workflow map and examining the practical value it creates for the team.
  • The content covers how to produce usable test evidence, how to verify workflow outputs from the recipient's perspective, and how to make a simple, honest estimate of business impact — in terms of time saved, consistency improved, or repeated work removed.
  • This section ends with a tested, validated workflow and a first business-impact view of what the automation actually delivers in practical terms.

Check 1
Did the trigger fire on the right row and at the right moment?

What to verify
Confirm the trigger fired only when the status reached exactly the agreed value — not on row creation, unrelated edits, or a variant spelling. The trigger log should show one event, not multiple.
Check 2
Are all required fields present and correctly mapped in the action step?

What to verify
Inspect the action node input. Task name, approver, brief link, owner, and due date should all be present. If any field is missing here, the message will be incomplete regardless of what the output looks like.
Check 3
Did the message reach the correct approver?
Click to reveal →
What to verify
The notification should have gone to the person named in the Approver field of the triggered row — not a test address, not an empty recipient, and not the person who built the workflow.
Check 4
Would the approver know what to do after reading the message?
Click to reveal →
What to verify
Read the notification from the approver's perspective. Does it name the task, identify who submitted it, state the due date, and link to the work? If they would need to send a follow-up message before beginning the review — the handoff is still incomplete.
Estimating business impact honestly

A useful estimate asks three questions: How much time did the automated step previously take per occurrence? How often does this step occur? What is the risk of the step being missed or done inconsistently? The answers to these three questions define the practical value of the automation — not just its technical performance.

Input quality determines output quality — click each to compare

Input: "We need to notify people when tasks are ready."

Result: AI returns a generic notification workflow with no connection to the team's tools, actual fields, or real process. Requires complete rewriting. The team spent more time correcting it than building from scratch.

Input: "We use Google Sheets and Slack. When the status changes, send a message."

Result: AI returns a basic trigger-action structure but does not include the right fields, conditions, or failure paths. Better than vague, but still requires significant adjustment before it is usable.

Input: "We have a Sheets tracker with status, approver, brief link, and due date. When status changes to exactly 'In Review', notify the approver via Slack with task name, owner, brief link, and due date. Approver field must not be empty. No duplicate sends for the same trigger."

Result: AI returns a workflow draft that includes the trigger condition, required fields, deduplication logic, and a suggested message format. The team spent four minutes reviewing — not rebuilding from scratch.

Strong vs weak AI usage in automation

The difference is not the tool — it is what the team keeps for themselves. A team that maps the workflow carefully before using AI gets better suggestions, evaluates them more confidently, and knows which ones to accept, modify, or reject. A team that asks AI to design the workflow from scratch cannot evaluate what they receive, because they never did the thinking themselves.

Section 3

Learning Objectives

Fourteen measurable outcomes that define what a trainee should be able to do after completing this session.

After this session, the trainee should be able to:
  • Identify
    repeated workplace tasks that are suitable for automation across multiple tools — and distinguish them from steps that require human judgment.
  • Distinguish
    between manual workflow steps and automation-ready steps based on whether the step is rule-based, repeated, and judgment-free.
  • Map
    a workflow clearly in terms of trigger, incoming data, transformation steps, destination action, and expected output — before opening any automation tool.
  • Explain
    API concepts practically as part of how tools exchange information inside a connected workflow — without needing technical depth.
  • Build
    a basic cross-tool automation in Zapier using trigger setup, field mapping, transformation, and action configuration — connected to the team's actual tools and data.
  • Build
    the same workflow logic inside n8n and recognise the structural and experiential differences between the two tools when building an identical automation.
  • Apply
    input validation, retries, logging, and simple failure handling to reduce fragile automation behaviour and prevent silent failures in a real workflow.
  • Recognise
    where rate-limit awareness and controlled workflow design matter in practical automation — and why these considerations affect reliability in production.
  • Extend
    a workflow with branching logic, approval gates, return paths, escalation paths, and failure handling so that it can handle more than one outcome from the same trigger.
  • Analyse
    a workflow using test evidence, expected output checking, and basic audit-trail thinking — and identify whether the automation is working at the human layer, not just the technical layer.
  • Estimate
    the practical business impact of an automation in terms of time saved, consistency improved, or manual work removed — as a first grounded assessment of the workflow's value.
  • Apply
    prompt engineering to support workflow design, condition drafting, test-case generation, troubleshooting, and workflow documentation using AI as a design partner.
  • Compare
    manual workflow design and AI-assisted workflow design as two approaches to building the same automation logic — and articulate what each approach contributes.
  • Produce
    a usable automation workflow that connects tools safely and clearly, with defined failure paths, tested outputs, and an identifiable owner responsible for its ongoing reliability.
How to use these objectives

Each objective maps to a specific teaching stage in this session. If a concept or skill listed above feels unclear after the session, refer back to the corresponding detailed outline block above to revisit the delivery flow and key framing for that stage. These objectives also serve as a self-assessment checklist when reviewing your own automation work after the session.
