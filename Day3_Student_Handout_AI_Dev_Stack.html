1 · What this day is about

AI-assisted development is not a shortcut around engineering process.

Day 3 teaches how to use AI tools inside an engineering workflow while keeping control over scope, context, access, testing, review, and human judgment.

Weak mindset
Start with the tool name.
Ask for code immediately.
Trust the explanation because it sounds confident.
Treat repo or command access as automatically safe.
Stronger mindset
Start with the task shape.
Ask for a plan before code.
Inspect the diff, tests, logs, and runtime behavior.
Give only the access that the task needs.

Core idea: Do not judge AI engineering tools by speed or demo impressiveness. Judge them by task fit, context access, workflow control, and verifiable evidence.

4 · Section reference

Use this as your quick reference during the session.

Open each section to review the core idea, decision rules, and what to watch for.

1
Tool Fit — task shape before tool name
+

Engineering task types

  • Implementation: add or change product behavior.
  • Refactoring: improve structure without changing behavior.
  • Debugging: investigate unknown cause before patching.
  • Tests: prove important behavior and edge cases.
  • Documentation: explain decisions, usage, or tradeoffs.
  • Repo investigation: understand existing code paths and patterns.
  • Review support: inspect diffs and possible risks.

Tool pattern choices

  • Editor-native agent: close to the code being edited.
  • Terminal / CLI agent: useful when commands, tests, and repo operations matter.
  • Connected-tool agent: useful when tickets, docs, issues, or design files matter.
  • Review / automation support: useful for diff inspection, summaries, checks, and reminders.
Ask first: What task am I doing, what context does it need, what output should I inspect, and what evidence will prove it worked?
2
Context + Access — what the AI can see, reach, and use
+
Access level
What it changes
Prompt only
Can be useful for general reasoning, but may miss project-specific behavior.
Single file
Can edit local logic, but may miss related modules and contracts.
Module / feature area
Can follow related code paths and preserve local patterns better.
Full repo
Can trace dependencies, conventions, tests, and existing architecture.
Command access
Can run tests, lint, builds, and reproduction steps; requires stronger review.
Connected systems
Can use issues, docs, designs, databases, or tickets; increases responsibility and risk.
Remember: more access is not always better. The goal is the right access for the task, paired with the right review standard.
3
Coding Workflows — plan before code, inspect before accepting
+
Stronger AI-assisted implementation loop
1 · Define
State the feature, scope, constraints, and what must not break.
2 · Context
Point the tool to relevant files, modules, ticket, acceptance criteria, and existing patterns.
3 · Plan
Ask for an implementation plan before code. Review the plan for wrong scope or wrong files.
4 · Implement
Keep the change small enough that the diff can be inspected.
5 · Inspect
Review diff, edge cases, tests, runtime behavior, and side effects.
6 · Decide
Keep, revise, reject, or roll back based on evidence.
Weak request
Build the escalation status feature.
Stronger request
For the support escalation workflow, inspect the existing SLA status logic and propose a small plan to add “approaching breach” handling without breaking current open, blocked, and resolved states. Do not code until the plan is reviewed.
4
Debugging + Tests — investigate before patching
+
Do not start with: “Fix this bug.” That is often too early because the cause is still unknown.
Debugging loop
Observe
What exactly failed? What is visible in UI, API, logs, or test output?
Hypothesize
List possible causes instead of accepting the first explanation.
Reproduce
Create a clear way to make the failure happen again.
Trace
Find where the value, state, or behavior changes incorrectly.
Patch
Change the smallest responsible area.
Verify
Run the test or check that proves the original failure is resolved.
Example: If backend status says “approaching breach” but the frontend badge says “normal,” inspect calculation, API contract, mapping, and UI rendering before patching.
5
Verification — evidence before trust
+
Diff

What changed? Is the change small, relevant, and aligned with project patterns?

Tests

Do tests cover the changed behavior and important edge cases?

Logs

Do logs or traces support the explanation of the fix?

Runtime

Does the feature behave correctly when actually run?

Decision
Use when...
Keep
The change is scoped, tested, reviewed, and matches the intended behavior.
Revise
The idea is useful, but the implementation needs adjustment.
Reject
The approach is wrong, risky, unclear, or not supported by evidence.
Roll back
The change created damage or uncertainty that should not move forward.
6
Staying Current — official sources and refresh habits
+

AI engineering tools change quickly. A workflow built on old assumptions can become weak even if it used to be correct.

Use official sources

Check product docs, changelogs, release notes, and official announcements when capability matters.

Refresh before teaching or using

Before relying on a tool behavior, confirm whether access, agent behavior, pricing, or limits have changed.

Separate stable principles from changing features

Task fit, evidence, and review stay stable. Specific tool capabilities can change quickly.

7
Agent Workflows — bounded, visible, reviewable loop
+
Agent workflow template
Trigger
What starts the workflow? Ticket, failing test, issue, PR, or human request?
Task
What exactly should the agent investigate, change, summarize, or verify?
Scope
What files, modules, commands, or systems are in scope? What is out of scope?
Access
What can the agent read, run, or edit?
Loop
How does it plan, act, report, and pause for review?
Evidence
What diff, tests, logs, or reasoning must it provide?
Decision
Where does the human decide: keep, revise, reject, or roll back?
Strong agent workflow: it does not hide the human. It makes human judgment more deliberate, visible, and defensible.
5 · Core rules to remember

The rules that protect AI-assisted engineering work.

Name the engineering task before naming the tool.
A tool that writes code is not automatically the right tool.
Context is not decoration; it changes what the AI can safely do.
More access is not always better access.
Debugging starts with evidence, not with a patch.
The AI explanation is not the object under review; the change is.
Verification ends with a decision: keep, revise, reject, or roll back.
Tool knowledge becomes stale; refresh from official sources.
Agent workflows should be bounded, visible, and reviewable.
Human judgment stays in the loop where the risk is real.
6 · Glossary

Key terms from Day 3.

Task fit +
Choosing an AI tool or workflow based on the actual engineering task, not the tool brand or demo quality.
Tool pattern +
The way a tool works inside the workflow, such as editor-native, terminal / CLI, connected-tool, or review-support pattern.
Context access +
What the AI can see or use: prompt text, files, modules, repo, commands, tickets, docs, or connected systems.
Command access +
The ability for an AI tool to run commands such as tests, lint, build, or reproduction steps. It is useful but raises the review bar.
MCP / connected access +
A practical way for AI tools to connect to external systems for relevant context, such as docs, tickets, repositories, or internal tools.
Plan-first workflow +
A workflow where the AI proposes a plan before writing code so the human can catch wrong scope, wrong files, or weak assumptions early.
Evidence-backed debugging +
Debugging that starts from observed failure, reproduction, traces, and tests before accepting a fix.
Verification evidence +
The proof used to judge a change: diff, tests, logs, runtime behavior, and review notes.
Agent workflow +
A bounded workflow where an AI agent has a defined trigger, scope, access, loop, evidence requirement, and human decision point.
7 · Self-check

Use these questions before you say “the AI helped.”

Can I name the engineering task clearly before choosing the tool?
Can I explain which workflow pattern fits this task?
Can I define what context the AI needs and what access it should not have?
Can I ask for a plan before code when the task affects real implementation?
Can I inspect the diff instead of trusting the explanation?
Can I reproduce a bug before accepting a patch?
Can I identify the tests or logs that prove the change works?
Can I decide whether to keep, revise, reject, or roll back?
Can I check official sources when a tool capability may have changed?
Can I design an agent workflow with a visible human checkpoint?

Final takeaway

AI does not remove engineering responsibility. It increases the need for clear task framing, controlled access, visible workflow, and evidence-based review.
